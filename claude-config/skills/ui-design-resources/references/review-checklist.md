# 実装後セルフレビュー チェックリスト

designsystemchecklist.com の観点をベースにした、実装直後の自己点検用リスト。
可能なら designsystemchecklist.com もフェッチして最新の観点を補う。

**使い方**: 今回触った範囲に該当する項目だけを、実際に画面とコードを見ながら確認する。
頭の中で「たぶん大丈夫」と流さず、該当箇所を実際に開いて確かめる。
問題が見つかったら報告して終わりにせず、直すところまでやる。
ただしトークンの変更などプロジェクト全体に影響が及ぶ修正は、実行前にユーザーへ確認する。

---

## 0. ブラウザ既定スタイルの残り

**画面を実際に見るまで気付けない類の不具合。** リセットCSS(normalize.css 等)を入れていない
プロジェクトでは、ブラウザが勝手に付けるスタイルが残り、意図した見た目にならない。
「トークンは正しいのに、なぜかこの部品だけ浮いて見える」ときは、まずここを疑う。

- [ ] `<button>` に `background` を明示したか
  — 既定で灰色の背景を持つ。枠線だけのボタンを作ったつもりが、塗り潰しに見える
- [ ] `<button>` / `<input>` / `<textarea>` に `font: inherit` を指定したか
  — フォントを継承しないため、そこだけ別の書体・サイズになる
- [ ] 固定サイズにしたい要素に `flex: none` を付けたか
  — flex/grid の子要素は既定で縮む。`width` の指定だけでは守られない
- [ ] `<ul>` / `<h1>`〜`<h6>` / `<p>` の既定の余白を打ち消したか、または意図して使っているか
- [ ] `:focus` の `outline` を消していないか(消すなら代わりの見た目が必ず要る)

コードを読むだけでは判断できない。**必ず実際の画面で確認する。**

## 1. トークンの一貫性(最優先)

- [ ] 色・余白・角丸・シャドウ・アニメーション時間が、すべてトークン経由になっているか
- [ ] 外部から取り込んだ部品にハードコードされた値が残っていないか
- [ ] 新しく増やした値はあるか。あるなら、それは本当に既存の段階で代用できなかったか
- [ ] 同じ役割の要素(例: すべてのカード)で、余白と角丸が揃っているか

## 2. 色

- [ ] 本文のコントラスト比 4.5:1 以上、UI部品の境界・大きい文字は 3:1 以上か
- [ ] 色だけで情報を伝えている箇所は無いか(エラーを赤字だけで示していないか。アイコンや文言も添える)
- [ ] ダークモード対応をしているなら、両モードで確認したか

## 3. タイポグラフィ

- [ ] 使っているフォントサイズの種類が、決めた段階の中に収まっているか
- [ ] 見出しレベル(h1〜h6)が、見た目の大きさではなく文書構造として正しい順序か
- [ ] 本文の1行が長すぎないか(45〜75文字程度)
- [ ] 日本語と英数字が混在する箇所で、行間や字間が破綻していないか

## 4. 余白とレイアウト

- [ ] 関連する要素どうしが近く、無関係な要素と離れているか
- [ ] 要素の左端(または基準線)が揃っているか
- [ ] コンテンツが長い / 短い場合の両方でレイアウトが崩れないか
- [ ] 文字を大きく設定しているユーザーでも破綻しないか(固定高さで文字が切れないか)

## 5. コンポーネントの状態

見落としが最も多い箇所。**動く部品は、すべての状態を1つずつ確認する。**

- [ ] hover / focus / active / disabled / loading の見た目が定義されているか
- [ ] 空の状態(データが0件)の表示があるか
- [ ] エラー状態の表示があるか。何が起きたか、どうすればいいかが書かれているか
- [ ] 読み込み中の表示があるか(スピナーやスケルトン)

## 6. アクセシビリティ

- [ ] キーボードの Tab だけで操作を最後まで完了できるか
- [ ] フォーカスされている要素が視覚的にはっきり分かるか(`outline` を消していないか)
- [ ] アイコンのみのボタンに `aria-label` があるか
- [ ] 画像に `alt` があるか(装飾目的なら `alt=""`)
- [ ] フォームの入力欄に `<label>` が紐づいているか(プレースホルダーはラベルの代わりにならない)
- [ ] モーダルを開いたとき、フォーカスがモーダル内に移り、Esc で閉じられるか

## 7. モーション

- [ ] アニメーションの時間が決めた段階に収まっているか
- [ ] 入場 `ease-out` / 退場 `ease-in` になっているか
- [ ] `prefers-reduced-motion` への対応があるか
- [ ] 何度も繰り返し見る操作のアニメーションが、長すぎて邪魔になっていないか

## 8. レスポンシブ

- [ ] モバイル幅(375px)で横スクロールが発生していないか
- [ ] タップ対象が十分な大きさか
  - **最低 24×24 CSS px** — WCAG 2.2 の必須基準(AA)。テキストリンクもここは満たす
  - **アイコンだけのボタンは 44×44 を目安に** — AAA相当の水準だが、指で押す前提なら実質必要。
    ラベルが無いぶん、押す場所が視覚的に分からないため
  - 実測で確認する。`width` を指定していても、flex/grid の中では潰れて足りなくなることがある
- [ ] テーブルなど幅の広いものが、はみ出さず自身の中でスクロールするか

## 9. アイコン

- [ ] 使っているアイコンセットが1つに統一されているか
- [ ] サイズと線の太さが揃っているか
- [ ] 隣接するテキストと視覚的な中心が揃っているか

## 10. ライセンスと安全性

- [ ] 取り込んだ部品のライセンス条件を確認したか
- [ ] 有料 / 要確認のアイコンセットを、ユーザーの確認なしに使っていないか
- [ ] 取り込んだコードに、要件と無関係な外部通信や不審な処理が含まれていないか

## レビュー結果の伝え方

ユーザーに報告するときは、以下の形で伝える:

1. **直したもの** — 何が揃っていなかったのか、どう直したか
2. **相談したいもの** — 全体に影響するため勝手に直さなかったもの
3. **今回は見送ったもの** — 気付いたが今回の範囲外と判断したもの、その理由

専門用語には一言の説明を添える。何をなぜ直したかが伝わらないと、次回から自分で判断できないため。
