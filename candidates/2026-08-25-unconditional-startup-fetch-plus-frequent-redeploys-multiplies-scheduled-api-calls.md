# [候補] 「起動時に1回だけ即時実行」するスケジューラーは、頻繁な再デプロイと組み合わさると意図した間隔より高頻度にAPIを呼んでしまう

observed_in: [kabu-simurator-app]
tags: [scheduler, cost-control, deployment, node]
date: 2026-08-25

## 何が起きたか
「起動直後は判断材料が無いので、1回だけ即時取得してからN分おきのループに入る」という設計のスケジューラー(Web検索を伴うAIによるニュース要約、既定24時間に1回)を実装していた。ユーザーから「呼び出し回数が体感で多い」という指摘を受けて調査したところ、意図通りに24時間に1回しか呼ばれていないはずが、実際にはもっと頻繁にAI呼び出しが発生していた。

## わかったこと・今の対応
原因は、開発中に何度も`git push`→Railway再デプロイ(SIGTERM再起動)を行っており、そのたびに「起動直後の即時取得」が無条件で発火していたため。スケジューラーの間隔設定自体(24時間)は正しかったが、「起動時に1回」という無条件の即時実行ロジックが、通常運用では滅多に発生しない「再起動」というイベントと結びついていることを見落としていた。対応として、起動時にDB上の既存キャッシュの生成時刻を確認し、設定した間隔内(24時間以内)ならその即時取得をスキップし、代わりに`最終取得時刻`の状態をDBの値で復元するようにした。ローカルで実際にサーバーを2回連続起動し、2回目でAPI呼び出しがスキップされること(ステータスAPIの`lastAttemptAt`が再起動時刻ではなく元の取得時刻のまま変わらないこと)を確認し、本番デプロイ後も同様に再取得が起きていないことを確認した。

## 詳しい経緯
本番の`/api/scheduler-status`相当のエンドポイントで実際の`lastAttemptAt`を見比べ、想定より新しい値になっていることから「起動のたびに再取得している」という仮説を立てて実装を確認した。この日は機能追加のため複数回デプロイしており、通常の運用頻度(1日1回程度のデプロイ)であれば気づきにくいレベルの余分な呼び出しだったが、開発が活発な時期には無視できない差になっていた。

## まだ確認できていないこと
- 同様の「起動時に1回だけ即時実行」パターンが他の間隔(価格ポーリング5分おき等、コストの低い処理)にも残っているが、そちらはコストが無視できるレベルのため対応不要と判断した。より高コストな処理を追加する際は同じ落とし穴に注意する必要がある
- キャッシュの生成時刻をDBではなくメモリ上だけで持っている構成(再起動でメモリが必ず消える構成)の場合は、この「DBの既存キャッシュを見てスキップする」対策自体が使えないため、別の対策(例: 起動時刻を外部に永続化する)が必要になる
