# [候補] `.table td { color: ... }` のような要素+クラスのCSSセレクタが、`.positive`/`.negative` 等の単一クラスの色指定を詳細度で静かに上書きする

status: candidate
observed_count: 1
observed_in: [kabu-simurator-app]
tags: [css, specificity, css-modules, frontend]
date: 2026-08-24

## 何が起きたか
株価アプリで「上昇=緑、下降=赤」の色分けクラス(`.positive`/`.negative`/`.buyTag`/`.sellTag`)をテーブルのセルに適用していたが、実際のブラウザでは常に白色(`--color-text`のデフォルト値)で表示され、色分けが一切機能していなかった。見た目には正しいクラス名がDOMに付与されており、CSS自体の記述ミスも一見なさそうに見えた。

## わかったこと・今の対応
共通スタイル側の `.table td { color: var(--color-text); }`(要素セレクタ`td` + クラスセレクタ`.table`の組み合わせ、詳細度 0,1,1)が、`.positive`(詳細度 0,1,0)より詳細度で勝っていたため、後から読み込まれる/されないに関わらず常に`.positive`側の`color`指定を上書きしていた。`getComputedStyle()`で該当要素の実際の色を確認したことで発覚。修正は`.table td`側の`color`宣言を削除するだけ(`--color-text`は`:root`からの継承でどのみち同じ値になるため、削除しても見た目に副作用がない)。

## 詳しい経緯
ユーザーから「全体的に白黒で見づらい」という漠然とした報告を受けたが、実際には配色設計自体は間違っておらず、この詳細度バグにより意図した色が一度も描画されていなかったことが根本原因だった。「色が薄い/地味」という主観的な報告を鵜呑みにして配色のトーン調整だけで対応していたら、根本原因を見逃していた可能性が高い。

## まだ確認できていないこと
- CSS Modules環境([xxx].module.css)以外(Tailwind等のユーティリティファースト環境)でも同種の「共通コンポーネントの要素セレクタが個別ユーティリティクラスを上書きする」問題が起きやすいかは未検証。ただしCSS詳細度のルール自体はどの環境でも同じなので、テーブルやリストのような「共通ラッパーコンポーネント内で個別に色をつけたいセル」がある設計では一般的に注意が必要と考えられる。
